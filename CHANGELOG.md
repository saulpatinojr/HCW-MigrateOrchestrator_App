- CI (2026-11-14, [HCW-HybridCloudWorks#1707](https://github.com/saulpatinojr/HCW-HybridCloudWorks/issues/1707)): **the workflow runtime check is brought up to the website's round five, the last planned round: a step whose `shell:` is written but empty now uses the job's or the workflow's default shell.** `tests/security/workflow-runtime-setup.test.mjs` (part of `npm test`) is the test that fails a workflow step that runs Node.js or Python before its job has chosen the version, so the GitHub runner's own older versions cannot slip in. Its checking logic and test cases are copied unchanged from the website's copy ([HCW-HybridCloudWorks#1726](https://github.com/saulpatinojr/HCW-HybridCloudWorks/pull/1726); single quotes written as double quotes, `expect` written as `assert`), the same as the Python copies ([HCW-NetworkEyes_App#405](https://github.com/saulpatinojr/HCW-NetworkEyes_App/pull/405)) and the AddOn's copy (changed the same way in its own pull request). What that means in practice: a step can carry a `shell:` line with nothing useful in it (`shell:` alone, `~`, `null`, only a comment, `''` or `""`), and GitHub's runner then uses the job's `defaults.run.shell`, else the workflow's, as if the line were not there. The check read such a step as using the runner's plain default shell, so a default such as `sudo python3 {0}` (the runner's own Python, through sudo) went unreported; now it is reported, and `pipx` is read under that default too. This copy's line reader already reads every one of those forms as empty text, and already gives a job with a null `defaults.run.shell` the workflow's (since [HCW-MigrateOrchestrator_AddOn#80](https://github.com/saulpatinojr/HCW-MigrateOrchestrator_AddOn/pull/80)), so only the shared logic changes. The header also records the owner's decision of 2026-11-14 on when the check changes from now on: round five is the last planned round. After it, this check changes only when (1) a real HCW workflow trips it or would get past it, or (2) a reviewer shows a way past it that a workflow could plausibly be written with. Any other edge case a reviewer raises is added to the known-limits list in the test file's header, not to a new round. No workflow here uses these forms, so nothing new is found; the file grows from 100 to 105 tests.

The expressions were also rewritten so a crafted line of 100,000 characters cannot make them slow (CodeQL alert 2, `js/polynomial-redos`): the old code took about 3 seconds on a line of repeated `eyJ`, and a new test runs twelve hostile 100,000-character lines and requires each to finish in under a second. `observability` is bundled into the published `@hybridcloudworks/migration-core`, so the downstream edition receives this with the next release. Tests (fake values only) are in `packages/observability/src/observability.test.ts`. Not in this change: CodeQL alerts 1, 3 and 4 (the same kind of problem in other files) and alerts 5 to 8; they stay open on #77.
- Security follow-ups from the independent review of pull requests 78 and 79 (issue 83): (F8) `docker-compose.appliance.yml` now publishes the API on `127.0.0.1:8081` only, and the API has a new optional `AMO_ALLOWED_HOSTS` list; when it is set, a request whose `Host` header is not on the list gets `421`, which stops DNS rebinding from reaching the public health and agent-list routes (an IP address as the Host is always served; the compose file sets it for local use; it is empty by default, which is right in Azure, and the Terraform does not set it). (F10) The worker no longer reads `AMO_ALLOWED_ORIGINS` or `AMO_ALLOWED_HOSTS`, so a bad value meant for the API cannot stop it. (F6) In `release-cli.yml` the attestation check moves from the `attest` job, which can sign, to a new job `verify-attestations` with read-only scopes; `attest` runs no repository script and no longer checks the repository out (ADR-0034 updated). (PR 78) `principal_object_id` in `app_role_assignments` must now be a GUID (and is lower-cased before it reaches Entra, which returns lower case), and a new test fails if `.terraform.lock.hcl` keeps fewer than five platform checksums per provider (a lock file regenerated on one platform would still pass Linux CI).
- Security (ticket AMO-13, issue #77, CodeQL alerts 1 and 3 to 7): four regular expressions that a crafted input could make slow are replaced by loops that read each character once, and two escaping gaps are closed. `tfName()` in `@amo/terraform-generator` (trimming underscores from a CSV display name, alerts 3 and 4; it now lives in one place, `tf-name.ts`, instead of two copies) and the new `embedsPassword()` in the appliance API (the check that a database address carries no password, alert 1) took about 3.5 seconds on a 100,000-character crafted value and are now instant. The Markdown table-cell escapers in `@amo/report-engine` and `scripts/refresh-rules-from-learn.mjs` (alerts 6 and 7) now escape a backslash before a pipe, so a backslash in a resource name can no longer cancel the pipe escape and split a table row. A no-op `replace(/^/gm, "")` in the state-impact script (alert 5) is removed; the output is unchanged. Visible effect: a backslash in a resource name or note now shows doubled (`\\`) in the Markdown reports (it was passed through before), so a backslash in front of a pipe can no longer cancel the pipe's escape and split a report row. Each fix has a test that failed before the change. Alert 8 (a test that asserts the shipped packages do not contain `management.azure.com`) is a right-but-intended check and is left for the owner to dismiss as Used in tests. Nothing in a package's public surface changes; the two new files are internal.
- Security (ticket AMO-13, issue #77): `ingestResourcesCsv()` in `@amo/csv-ingestion` now has a per-cell length limit, `maxFieldLength`, default 65,536 characters (`DEFAULT_INGEST_LIMITS.maxFieldLength`). A row with a longer cell is skipped and the warning names the row and column but not the value; a header cell that long refuses the file. Before, the only limits were 5 MB for the whole upload and 5,000 rows, so one cell could be 5 MB, and the web-front edition (`HCW-MigrateOrchestrator_AddOn`) passes only those two limits, so it gets this one by default. The longest real value is a few thousand characters: an Azure resource id is about 2,000 and the tags cell is at most about 40,000. A new optional field and a new default property are the only public-surface change; behaviour changes only for a cell longer than 65,536 characters. The next release carries it, and the add-on's `docs/whats-new-upstream.md` should say so when it adopts that release.
