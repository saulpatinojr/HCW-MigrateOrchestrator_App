- Fix (found by the first sandbox apply, 2026-10-26; the item "PostgreSQL Entra token exchange at connect time ... untested live" in `docs/deployment/enterprise.md` section 5): the API and the worker exited at start on an Azure database with the log line `fatal: unhandled error, exiting`. The cause: `repositoryFromEnv` gave `pg` a connection string and a `password` function together, and with `pg` 8.23.1 the connection string replaces the function with `null`, so the server received an empty password and answered "Password returned by client is empty". For a non-local database the pool is now given separate fields (host, port, user, database, TLS, the token provider) and no connection string; a local database keeps its connection string. TLS is now always on and verified for a non-local database, whatever `sslmode` the address says, because the password is an access token. A malformed address is refused without echoing it. Options in the address are not dropped: `application_name` and `options` (server settings such as `-c search_path=...`) are passed on, a `sslmode` weaker than `require` is refused, and any other option is refused by name, so a deployment can never silently run without a setting it asked for; an option repeated in the address is refused too, because its first value would win here but its last value in `pg`'s own parser. New tests in `apps/appliance-api/src/entra-pool-config.test.ts` use the real `pg` library to prove the token provider survives; the earlier test used a fake pool, which cannot show that. As of 2026-10-26 not yet proven live. The corrected image was then published as `v0.4.1` and, on 2026-10-27, deployed to the sandbox, where the database login is indicated (start-up order and the teardown) but no query was run; see the first sandbox apply entry above.

- Security (issue [91](https://github.com/saulpatinojr/HCW-MigrateOrchestrator_App/issues/91)): `repositoryFromEnv()` decided that a database address was "local" when the text `localhost`, `127.0.0.1` or `@postgres:` appeared anywhere in it, so `postgres://user:secret@db.example.com/amo?application_name=localhost` skipped the two rules for a real server (no password in the address; an Entra credential is required). It now decides from the parsed host name: `localhost`, `127.0.0.1`, `[::1]` or the Compose service `postgres`. An address that is not a URL (a libpq `host=... dbname=...` string) is never local and gets the stricter rules. Tests in `local-database.test.ts` cover `?application_name=localhost`, a user name `localhost`, look-alike hosts and `@postgres:5432`.

- Security (issue [83](https://github.com/saulpatinojr/HCW-MigrateOrchestrator_App/issues/83), F-05; ADR-0031 amendment; decided by the owner): two-person approval for Resource Mover. An approval recorded by the person who then asks to execute no longer counts for `initiateMove` (`production-deploy`) or `commit` (`data-cutover`): the API answers 403 with a reason naming the two-person rule, and a second `Migration.Execute` holder must record the approval. New explicit opt-out `AMO_ALLOW_SELF_APPROVAL=true` for a lab or a single-operator appliance: off by default, never set by the Terraform, the image or Compose (which only passes it through), refused at startup for any value other than `true` or `false`, ignored by the worker, and every execution that used the caller's own approval is audited with `selfApproval: true`. **Behaviour change for existing deployments:** a single operator who approved and executed their own moves must now either have a second person approve or set the opt-out. Tests: two principals over HTTP, the opt-out, and mutation checks (`two-person-approval.test.ts`, `self-approval-default.test.mjs`). The existing single-principal API tests set the opt-out explicitly.

- The appliance API allows cross-origin browser calls only from an exact-match allow-list (ticket AMO-3, issue 44, ADR-0033; decided by the owner on 2026-10-25, row C3 of the portfolio issue 1373, replacing an earlier same-origin-only call the same day): new environment variable `AMO_ALLOWED_ORIGINS`, a comma-separated list of exact origins (`https://`, or `http://` for `localhost`, `127.0.0.1` or `[::1]` only; lower-case host, a port only when it is not the default, no path, no trailing slash). **Default empty = no CORS headers at all**, so a web UI on the same address keeps working with no setting. For an origin that equals an entry exactly, every `/api/` answer carries `Access-Control-Allow-Origin` with that exact origin and `Vary: Origin`; a preflight (`OPTIONS` with `Access-Control-Request-Method`) from it is answered `204` before the authentication guard with `Access-Control-Allow-Methods: GET, POST, OPTIONS`, `Access-Control-Allow-Headers: Authorization, Content-Type` and `Access-Control-Max-Age: 600`. There is no wildcard, no `Access-Control-Allow-Credentials` (bearer tokens, not cookies), and the `Origin` header is never copied into a response unless it matches an entry. A disallowed origin, a look-alike or a request with no `Origin` gets no CORS headers, and the request still needs its Entra token (validation on every protected route is unchanged; `/api/health` and `/api/agents` behave as before). A wildcard, `null`, an empty entry, a path, a trailing slash, an upper-case host or any malformed entry makes the API and the worker refuse to start with a message that names `AMO_ALLOWED_ORIGINS`. The code is `apps/appliance-api/src/cors.ts`. `docs/deployment/enterprise.md` section 2b documents the setting and keeps Azure Static Web Apps as an untested option with its Microsoft Learn limits; `.env.example` and `docker-compose.appliance.yml` carry the variable; the Terraform does not set it yet. - Security (ticket #46, role part; ADR-0031): the appliance API now requires an Entra app role. A valid token that carries none of `Migration.Read`, `Migration.Plan`, `Migration.Execute` or `Migration.Execute.Destructive` (no role, an empty `roles` claim, an unknown or differently cased role, or a `roles` claim that is not an array of strings) is refused with 403 on every protected route, including `/api/me`; before, it was silently treated as the `discovery` level. There is no default access any more. The owner decided (2026-10-25) to add a lowest role, **`Migration.Read`** (maps to the old `discovery` level: assess only, no move validation, plans, approvals or execution), together with Entra "assignment required"; an earlier draft had deferred it. Nobody has access until a role is assigned; `Migration.Plan` is wider than the old role-less access, so use `Migration.Read` for assess-only users. Terraform now creates the enterprise application (`azuread_service_principal.api`) with `app_role_assignment_required = true` as a first layer (Entra is meant to refuse unassigned users and applications; administrators who can manage the application are documented exceptions and the portal's "Default Access" is not a role, so the role check in the API is the authoritative control), and adds the optional variable `app_role_assignments` (empty by default) plus outputs for the application's object ID and role IDs. **Enabling assignment locks out everyone without a role, including you, at apply time: put your own role in `app_role_assignments` in the same apply, or assign yourself in the portal at once.** Removing a role takes effect only when the person's existing access token expires. The enterprise application now sets `use_existing = true` and `prevent_destroy`; roll back by setting `app_role_assignment_required = false`, not by removing it. The web page now shows a plain message when sign-in is refused for lack of a role (`AADSTS50105`, unverified against a real redirect). Applying role assignments needs `AppRoleAssignment.ReadWrite.All` and `Application.Read.All` (or Application Administrator), and a pipeline holding that can grant itself `Migration.Execute.Destructive`: assign production roles by hand. **After deploying this, assign yourself a role** (steps in `docs/deployment/enterprise.md`) or nobody can sign in to use the appliance. Nothing existing was loosened: token validation, including the `nbf` check, is unchanged. Tests: missing, empty, wrong, look-alike and malformed roles, the four valid roles, the highest role winning, `Migration.Read` on every route (allowed routes answer, validation, approvals, execution and operations are 403), 403 on every route with nothing created for the caller, and a static test that the Terraform roles and the API's role table are the same set. `azure-auth` and the appliance are never published, so the published packages and the downstream edition are unchanged.
